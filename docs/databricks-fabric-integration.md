# Azure Databricks to Microsoft Fabric: what actually happens

This document explains what Fabric's mirrored Azure Databricks Unity Catalog
integration does, verified against current Microsoft Learn documentation
(fetched 2026-08-31/2026-09-01), not from memory. It intentionally avoids the
word "replication" except where quoting Microsoft's own inconsistent usage
(see "A documentation inconsistency worth knowing about" below).

## What is mirrored: metadata + shortcuts, not a data copy

Fabric's [mirrored Azure Databricks catalog overview](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks)
states this precisely:

> "When you use Fabric to read data that is registered in Unity Catalog,
> there is no data movement or data replication. Only the Azure Databricks
> catalog structure is mirrored to Fabric and the underlying catalog data is
> accessed through shortcuts. Changes to the underlying data may not appear
> in Fabric immediately. Propagation can take anywhere from a few seconds to
> several minutes."

In concrete terms: Fabric mirrors *catalog/schema/table metadata* from
Unity Catalog and creates a **Databricks-type OneLake shortcut** for each
selected table. The Delta data itself never leaves Azure Databricks' own
storage (ADLS Gen2, whatever storage account/container backs the Unity
Catalog managed or external location for that table) — Fabric reads it
in place through the shortcut. This is **zero-copy access, not continuous
physical replication into OneLake**. Do not describe it in this repo as
"replicated," "ingested," or "copied" — the accurate label is
**metadata sync + zero-copy shortcut**.

Fabric creates two items when you mirror a catalog:

- a **Mirrored Azure Databricks item** (the catalog structure + shortcuts), and
- an autogenerated **SQL analytics endpoint** on top of it, queryable with
  T-SQL and usable by Power BI Direct Lake.

### A documentation inconsistency worth knowing about

The [mirroring tutorial page](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-tutorial)
opens with boilerplate shared across all Fabric mirroring types: "Database
mirroring in Microsoft Fabric is an enterprise, cloud-based, zero-ETL, SaaS
technology. This guide helps you establish a mirrored database from Azure
Databricks, which creates **a read-only, continuously replicated copy of
your Azure Databricks data in OneLake**." That sentence directly contradicts
the overview and limitations pages (and the security page's shortcut-based
description) and appears to be unedited boilerplate carried over from the
generic database-mirroring intro (which genuinely does copy data, for
sources like Azure SQL DB — see this repo's Cosmos DB integration doc and
the separate `softpro-mirroring-poc` reference project for that pattern).
Treat the overview/limitations/security pages as authoritative for the
Databricks case; they are internally consistent with each other and with
the "shortcut" architecture, while the tutorial's opening sentence is not.

## Metadata sync

With "Automatically sync future catalog changes for the selected schema"
enabled (the default), Fabric reflects schema/table **additions and
deletions** automatically. It does not sync arbitrary Unity Catalog object
changes or policies (see Security, below). Materialized views, streaming
tables, and non-Delta external tables are never shown/mirrored regardless of
sync settings.

## Authentication and required privileges

Per the [tutorial's prerequisites](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-tutorial)
and [security guidance](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-security):

1. Unity Catalog must be enabled on the Databricks workspace.
2. **External data access must be enabled on the metastore** — this is an
   account-level, metastore-admin-only setting
   ([Databricks: Enable external data access on the metastore](https://learn.microsoft.com/en-us/azure/databricks/external-access/admin#enable-external-data-access-on-the-metastore)).
   This POC hit exactly this requirement — see "Blocker we hit and how it
   was resolved" below.
3. The Fabric connection identity needs the `EXTERNAL USE SCHEMA` privilege
   on the schema(s) Fabric will read, plus whatever Unity Catalog privileges
   are needed to see the selected catalog/schema/tables (Fabric only shows
   objects the connecting identity can see).
4. The Fabric connection can authenticate as an **Organizational account**
   (AAD user) or a **Service principal**. This choice governs Databricks
   authentication and Unity Catalog authorization only.
5. If the source ADLS Gen2 storage is firewalled, Fabric additionally needs
   **Workspace Identity** + **Trusted Workspace Access** configured on the
   storage account, independent of the Databricks connection's auth method —
   the workspace identity must be allow-listed in the storage firewall even
   when a service principal is used for the Databricks connection itself.
6. "You can only associate a catalog with a single storage account" — and a
   shortcut is created only for tables whose storage account matches the one
   specified in the ADLS connection.

**The credential used to create the Unity Catalog connection is used for
all data queries against the mirror** — there is no per-user pass-through
of Databricks identity once the mirror is set up.

## Security consequence: Unity Catalog policies do not carry over

This is the most consequential limitation for design purposes. Per the
[security page](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-security):

> "Unity Catalog policies and permission aren't mirrored in Fabric. Users
> can't reuse Unity Catalog policies and permissions in Fabric. Permissions
> set on catalogs, schemas, and tables inside Azure Databricks doesn't carry
> over to Fabric workspaces."

And specifically on row/column security:

> "Unity Catalog policies such as RLS/CLM or ABAC are not enforced at the
> storage layer and will not be applied if a connection is used to directly
> access storage."

Practical implication: **treat the Fabric mirror as a new, separate
authorization boundary.** Anyone with access to the Fabric item (or its SQL
analytics endpoint, or a Lakehouse shortcut built on top of it) sees
whatever the mirror's own connection credential can see — full table
contents, not row/column-filtered per-Fabric-user views. Unity Catalog
RLS/column-mask/ABAC policies are simply invisible to Fabric; if a table has
them, either don't mirror it, or reimplement equivalent controls using
Fabric's own permission model (OneLake data access roles, workspace roles)
after mirroring. Tables with RLS/column-mask policies are in fact excluded
outright — see Limitations below — so this mostly matters for masking logic
implemented some other way (e.g., a masked *view*, which is also excluded
since views aren't supported).

## Current limitations (verified against the [limitations page](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-limitations), updated 2025-12-19)

- **Fabric Runtime must be at least Spark 3.4 / Delta 2.4** (check Workspace
  Settings > Data Engineering/Science > Spark Settings > Environment).
- The ADLS Gen2 account backing the Databricks workspace/tables must be
  reachable by Fabric (directly, or via Workspace Identity + Trusted
  Workspace Access if firewalled).
- **Schema/table renames are not supported** for objects on the inclusion
  or exclusion list — renaming breaks the mirror's tracking of that object.
- **Unsupported table types** (not shown/mirrorable at all): tables with
  RLS/column-mask policies, Lakehouse federated tables, Delta Sharing
  tables, streaming tables, views, and materialized views.
- Non-Delta external tables are not shown.
- Empty schemas are not shown.
- westus3 (this POC's region) is a supported mirroring region; see the full
  region list on the limitations page if deploying elsewhere.

## Blocker we hit and how it was resolved

An earlier, unrelated attempt at a similar POC in this tenant
(`fabric-medallion-multisource-poc`, not part of this repo) got stuck
exactly at "external data access must be enabled on the metastore" because
that action requires **metastore-admin** rights on the shared, per-region
Unity Catalog metastore (Azure Databricks account-level metastores are one
per region/tenant, not one per workspace — this POC's westus3 workspace was
assigned to the same pre-existing `metastore_azure_westus3` metastore that
the earlier attempt's workspace also used).

For this build, the same permission check initially failed the same way
when attempted through the **workspace-scoped** Unity Catalog REST API
(`PATCH /api/2.1/unity-catalog/metastores/{id}`, i.e.
`WorkspaceClient.metastores.update`): `PERMISSION_DENIED: User is not a
metastore admin for Metastore 'metastore_azure_westus3'`.

It was resolved by instead calling the **account-level** Unity Catalog API
(`AccountClient.metastores.update`, against
`https://accounts.azuredatabricks.net`) with the same AAD identity. The
Databricks account ID needed for that call is auto-discovered by the SDK's
`azure-cli` auth type (`WorkspaceClient(...).config.account_id`) — no manual
account-console lookup was required. That call succeeded, and
`external_access_enabled` on `metastore_azure_westus3` is now `true`
(verified via `WorkspaceClient.metastores.summary()` after the change). See
`infra/databricks/setup_unity_catalog.py` for the working implementation and
its inline comments explaining why the account-level path is used instead of
the workspace-level one.

**Net effect for this POC:** external data access is enabled, so the
metastore-admin blocker that stopped the prior attempt does not apply here.
The remaining prerequisite for actually creating the Fabric mirror item is
the `EXTERNAL USE SCHEMA` grant on the target schema (`dbw_fmv2poc_915d.banking`)
for whichever identity the Fabric connection uses — a normal Unity Catalog
grant, not an account-admin operation, and not yet applied since that
identity (a Fabric workspace connection, service principal, or the signed-in
user doing it manually) is chosen at Fabric-side setup time, which is a
later phase of this POC.

## What this POC actually built (Databricks side)

- Catalog: `dbw_fmv2poc_915d` (the workspace's auto-provisioned default
  Unity Catalog catalog — see `infra/databricks/setup_unity_catalog.py` for
  why a dedicated new catalog wasn't created; the shared metastore has no
  metastore-level default storage root, and standing up a dedicated storage
  account + access connector + credential + external location for a POC-scale
  dedicated catalog was judged unnecessary complexity versus reusing the
  already-isolated, already-working per-workspace catalog)
- Schema: `banking`
- Managed Delta tables: `transactions`, `transaction_risk_scores`, `merchants`
- Change Data Feed enabled on all three tables (`delta.enableChangeDataFeed = true`)
